1. **High - Recovery can overwrite the task-only failure record.**

   **Claim attacked:** Recovery becomes safe by acquiring the task lock, while dispatch may record `launch-failed` without the project lock ([Spec:122](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/SPEC.md#L122)).

   **Facts:** [common.ts:266](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/src/core/commands/common.ts#L266) reads records, computes recovery in memory, and publishes later. The proposal requires lock ownership for writes but does not explicitly require rereading after acquiring that lock.

   **Inference:** B holds the project lock and reads A as `launching`. A exhausts its reacquisition timeout, records `launch-failed` under its task lock, then releases it. B acquires A’s task lock and publishes recovery from its stale copy. Every write obeys the proposed ownership rule, yet A’s failure reason, preparation outcome or history can disappear.

   **Why it matters:** Exclusive writes do not prevent stale read-modify-write updates.

   **Smallest correction:** Require acquisition before reading the authoritative task record, reread/revalidate lifecycle after acquisition, and retain ownership through publication or cancellation. Add a barrier test for this exact interleaving.

2. **High - The lock protocol does not define contention for every writer.**

   **Claim attacked:** Only a task-lock holder writes, and `collect`/`close` remain serialized ([TC-0004:291](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/contracts/TC-0004-project-preparation.md#L291)).

   **Facts:** The Spec defines nonblocking acquisition for dispatch and recovery, skipping busy recovery candidates, and `wrong-lifecycle` for a live `launching` task. It does not define acquisition, contention outcomes or release lifetime for ordinary `resume`, `collect` and `close`. Those commands currently rely on the project lock alone. `status` can also hold a task lock, so a busy task lock does not uniquely identify a live dispatch.

   **Inference:** Build must invent behavior for task-lock contention and decide whether recovery keeps locks across validation and deferred publication. Waiting while holding the project lock can obstruct the dispatch that holds the task lock and needs the project lock back.

   **Why it matters:** These choices change observable failures and progress guarantees.

   **Smallest correction:** Add a lock protocol table covering each command: acquisition order, waiting policy, busy result, authoritative read point and release point. Include refusal cleanup and status-held-lock cases.

3. **High - Preparation completion is undefined when descendants outlive their command.**

   **Claim attacked:** Commands run sequentially, preparation has a ten-minute limit, and the process group receives termination signals ([Spec:379](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/SPEC.md#L379)).

   **Facts:** Each command gets its own process group. Failure and completion are described through command exit status. P5 tests a child ignoring `SIGTERM`, but the contract does not define successful parent exit with surviving children.

   **Inference:** A command can spawn a background writer and exit `0`. Demerzel can start the next command or the agent while preparation still changes the worktree and log. At a later timeout, signaling only the current command’s group leaves an earlier group alive.

   **Why it matters:** “Prepared before the agent” and the whole-preparation deadline lack a defined completion boundary.

   **Smallest correction:** Specify descendant policy on normal exit and timeout, including which groups remain supervised and whether success requires quiescence. Test parent-exits-first, parent-exits-on-TERM, surviving child, and cumulative timeout across commands. Also prove that a surviving child does not retain the dispatch’s task lock after dispatch is killed.

4. **High - Git hooks execute outside the declared preparation boundary.**

   **Claim attacked:** Preparation is the only project code Demerzel runs, and its execution has bounded time and captured output ([Spec:695](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/SPEC.md#L695)).

   **Facts:** `git worktree add` precedes `prepare_started_at` and project-lock release. Installed Git documentation (`githooks.adoc`, line 209; see `git help githooks`) confirms that it invokes `post-checkout`. The existing [Git helper:6](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/src/core/git.ts#L6) inherits the supplied environment and has no timeout. Test fixtures deliberately exclude hooks.

   **Inference:** A configured hook can perform installation, network access or arbitrary work while the project lock remains held, before the preparation timer and log capture begin. The proposed tests can pass without exercising this path.

   **Why it matters:** This defeats the stated execution boundary and can reproduce the parallel-dispatch blockage the increment intends to remove.

   **Smallest correction:** Explicitly decide the policy for Git hooks and checkout-time executables. Either suppress them for core creation or document and bound their execution separately. Add a local hook fixture proving timing, output handling and failure reconciliation.

5. **Medium - Orphan preparation is acknowledged, but its interaction with `close` is not.**

   **Claim attacked:** Recovery produces `launch-failed`, while `close` retains its behavior ([TC-0004:244](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/contracts/TC-0004-project-preparation.md#L244)).

   **Facts:** [TC-0004:476](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/contracts/TC-0004-project-preparation.md#L476) explicitly permits preparation to continue writing after recovery. [close.ts:72](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/src/core/commands/close.ts#L72) protects working backend agents, then can close and discard the worktree. A preparation process has no backend agent.

   **Inference:** Recovery followed by close can mark a task closed, release its overlap reservation, and potentially remove a clean worktree while its preparer remains alive.

   **Why it matters:** `launch-failed` and `closed` cannot imply that task-associated execution stopped.

   **Smallest correction:** Preserve the non-goal of killing orphans, but explicitly define close/discard behavior and the diagnostic for potentially surviving preparation. Add a recovery-then-close test with a demonstrably live child. This requests a decision, not an expansion to automatic cleanup.

6. **Medium - An absent configuration is not distinguished from an unreadable Git object.**

   **Claim attacked:** Missing `.demerzel.json` means no preparation; malformed content means refusal ([Spec:346](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/SPEC.md#L346)).

   **Facts:** The specified read is `git show <commit>:.demerzel.json`. The text defines absence and invalid JSON but no outcome for object-read failure or an entry of the wrong Git type. The nearby integration currently treats any failed map read as absence ([radiant/dispatch.ts:88](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/src/radiant/dispatch.ts#L88)).

   **Inference:** Copying that pattern can silently skip preparation when Git failed for a reason other than a missing path.

   **Why it matters:** A repository requiring preparation could launch unprepared, contradicting the objective.

   **Smallest correction:** Define “absent” as a successfully inspected tree lacking the entry; specify accepted entry types and the refusal for read failures. Require no-effect tests for missing, malformed, wrong-type and unreadable objects.

7. **Medium - Read-only status and refusal tests conflict with reusing the existing lock primitive.**

   **Claim attacked:** `status` never writes, refusals have no effect, and existing test changes are narrowly restricted ([TC-0004:285](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/contracts/TC-0004-project-preparation.md#L285)).

   **Facts:** [lock.ts:40](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/src/core/lock.ts#L40) opens with `O_CREAT` and stamps the file by truncating and writing it. Spec §5 exempts only the project’s `lock`. The existing [task snapshot helper:82](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/test/core/helpers/sandbox.ts#L82) compares every file under `tasks/`, which will now include lock files.

   **Inference:** Direct reuse makes status mutate lock metadata and can make a refusal’s recovery probe change the task-directory snapshot. Conversely, excluding all lock files from assertions silently weakens the existing no-effect evidence.

   **Why it matters:** Build must choose the observable filesystem contract and amend tests outside the explicitly listed assertion changes.

   **Smallest correction:** Define allowed lock-file creation/stamping separately from task-state mutation, including legacy records without lock files. Provide a non-stamping observation path if “never writes” is literal, and explicitly authorize the corresponding helper changes while retaining JSON and resource invariants.

8. **Medium - “The next recovering command” conflicts with refusal without effect.**

   **Claim attacked:** After killed preparation, the next recovering command takes the task to `launch-failed` ([TC-0004:282](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/contracts/TC-0004-project-preparation.md#L282)).

   **Facts:** Recovery runs in `resume`, but [resume.ts:24](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/src/core/commands/resume.ts#L24) rejects a recovered `launch-failed` task before publishing recovery. This preserves Spec §5. An unrelated dispatch that refuses likewise must not publish recovery.

   **Inference:** The promised transition cannot hold for every next recovery-capable command without violating refusal-without-effect.

   **Why it matters:** Two reasonable tests can demand contradictory persisted states.

   **Smallest correction:** State that recovery is published only when the enclosing command proceeds past all refusals. Specify expected persisted state for `resume` after killed preparation and for an unrelated refused dispatch; require both tests.

9. **Medium - Successful preparation can invalidate the launch identity, with different results by harness.**

   **Claim attacked:** Successful preparation proceeds to the session, while the launch check remains unchanged ([TC-0004:266](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/contracts/TC-0004-project-preparation.md#L266)).

   **Facts:** Preparation permits arbitrary argv, including Git commands. Claude Code’s check requires the original branch and base commit; Codex has no corresponding check ([Spec:248](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/docs/project/SPEC.md#L248)). [backend.ts:413](https://github.com/faelplg/demerzel/blob/350e862c25b3dffc7ba5861ac8cdab615c7af5d0/src/herdr/backend.ts#L413) implements that distinction.

   **Inference:** Preparation that successfully commits, switches branches or detaches HEAD can launch Codex against a different identity, while Claude Code fails only after opening a session and starting its agent.

   **Why it matters:** The recorded base and validated contract may no longer describe the tree receiving the request.

   **Smallest correction:** Define the repository invariants preparation must preserve and the outcome when it violates them. If preserving branch/base is required, check it before session creation for both harnesses. Add a successful command that changes HEAD as a negative fixture.
