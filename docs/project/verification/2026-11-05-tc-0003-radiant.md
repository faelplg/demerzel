### Engineering notes

- Seis decisões de borda que a Spec não nomeia. Escolhi o código mais
  próximo que já existe e deixo para o owner confirmar. Todas recusam com
  `2` e sem efeito. Nenhuma muda o registro, o ciclo de vida ou o pedido.
  - `--base` que não resolve é `task-invalid`, o código que o núcleo já dava
    para a mesma checagem antes de a Spec 0.12 trazer a base para a
    integração.
  - Um ID de unidade fora de `TC-NNNN.N` é `unit-not-found`, antes do gate.
    Sem o prefixo, não há contrato a procurar.
  - Fora de um repositório Git, a integração recusa com `not-a-project`, o
    código do núcleo, porque ela roda antes dele.
  - `radiant.root` relativo é `config-invalid`, porque o pointer
    `radiant-root` precisa ser absoluto.
  - Um `agents.json`, `capabilities.json` ou `provides.json` fora do formato
    é `validator-failed`. É inalcançável num checkout limpo no pin, que o gate
    confere antes.
  - `--rule <id>` procura só em `rules`. Sem a flag vale `default`, e
    `--rule default` sem uma regra com esse ID é `routing-invalid`.
- Na recusa de `resume` por conferência que não confere, o motivo vai em
  `backend_error` da tarefa no envelope, como o `dispatch` já faz com o
  motivo de `launch-failed`.
- O passo do CI lê o pin com `python3`, porque o GitHub Actions não lê
  arquivo numa expressão. O comentário do passo `bun run check` foi
  atualizado para citar os testes da integração.
- Quando falta `DEMERZEL_RADIANT_ROOT` ou o checkout está fora do pin, o Bun
  conta uma falha por arquivo, a do `beforeAll`, e não uma por teste.
- O `bun run check` não rodou num clone limpo local. O `bun install` desse
  clone poderia precisar de rede, e a rede é negada ao Build. O CI, que parte
  de um clone limpo nos dois sistemas, é a evidência desse critério.

### Remaining limitations

- O `git check-ignore` roda no checkout chamador, como a Spec 3 diz. Um
  `.gitignore` do working tree diferente do commit base não é detectado.
- O `dispatch` e o `resume` com harness real não rodam neste contrato. O
  caminho real é exercitado pelo incremento 6.
- No pin, nenhum adapter declara `provides`. Um candidato que cobre
  `requires` e vence só é provado na função pura do roteamento.
- A detecção de `harness-without-adapter` depende do texto
  `harness without an adapter` do `check_dispatch.py` no pin, porque os erros
  não têm código.

### Learn Back candidate

- O `check_dispatch.py` devolve erros como texto livre. Um código por erro,
  ao menos para candidato sem adapter, tiraria do Demerzel a conferência de
  texto a cada mudança de pin.
- Um contrato que acrescenta um tipo de processo deveria listar os testes de
  guarda de contratos anteriores que ele precisa emendar. Aqui, o conflito
  com o teste de fronteira do TC-0002 só apareceu no Build e pediu uma emenda
  do owner.
