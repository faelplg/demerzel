## Findings

1. **Minor - T4 against the partial-confirmation tests and output 8.**

   **Finding:** T4 accepted a `tab create` answer only when its tab and root pane IDs agree and name the recorded workspace, and recorded nothing otherwise. Today `reportSession` in `src/herdr/backend.ts` records the resources a partial creation answer confirms before failing, and the tests for findings K2 and L2 of the TC-0002 verifications in `test/herdr/backend.test.ts` (no tab, no root pane, no workspace object, with and without a lost reconciliation snapshot) depend on it. Output 8 did not allow those tests to change. The contract had to choose between all or nothing and recording a tab from a partial answer.

   **Applied:** T4 is all or nothing. `tab.tab_id`, `root_pane.tab_id`, `root_pane.pane_id`, `tab.workspace_id` and `root_pane.workspace_id` must all be present as non-empty strings, the two tab IDs equal, and both workspace IDs equal to the recorded workspace, before the tab and the pane are recorded. A `workspace` object is not expected, since herdr 0.9.5 sends none. A partial or contradictory answer records nothing; the failure path finds the tab by its unique task label, and with that snapshot lost too, a later `close` finds it by label (X1). Output 8 now lists the partial-confirmation tests and says how they are rewritten, including "without the workspace object" becoming "without `tab.workspace_id`". A mutation was added for recording a partial answer. This is the option the owner preferred: no resource recorded without confirmation, and it matches what herdr 0.9.5 returns.

2. **Minor - exact history details for `tab-found`, `close-failed` and `closed`.**

   **Finding:** X1, X2, X4 and EB-07 did not fix the history detail shapes that replace today's `workspace-found` `{ workspace, by: "label" }`, `close-failed` `{ workspace, backend_error }` and `closed` `{ workspace_closed }`.

   **Applied:** X1 fixes `tab-found` as `{ tab: <found tab ID>, by: "label" }` and says `backend_ids.pane` is left as it is, also when `null`, and `created` is not changed by `close`. X2 fixes `close-failed` as `{ tab, backend_error }` and `closed` as `{ tab_closed, last_tab_in_workspace }`, with `tab_closed` `null` when no call was made. X4 says `last_tab_in_workspace` is `false` when another tab remains or the task's tab was not in the snapshot. The EB-07 row asks for whole-detail assertions.

3. **Minor - Portuguese `next` for `herdr.workspace_labels` refusals.**

   **Finding:** `src/cli/run.ts` wraps every `parseHerdrConfig` failure with the Portuguese `next` "Corrija o bloco herdr da configuração e rode de novo.", so a new English message would reach the user with a Portuguese `next`, against E1.

   **Applied:** output 6 now includes an English `next` for every `parseHerdrConfig` refusal in `src/cli/run.ts`, already in the allowed scope, which section 4 now names; C1 and E1 point to it. The existing `test/cli.test.ts` only asserts the code `config-invalid`.

4. **Nit - control characters in `herdr.workspace_labels` keys.**

   **Finding:** C1 forbade control characters in values only, and an offending key named in a message could break the line-oriented text output.

   **Applied:** C1 forbids U+0000 to U+001F and U+007F in keys too, and names an offending key with `JSON.stringify`. A mutation was added for both.

5. **Nit - test annotations in section 4.**

   **Finding:** section 4 annotated `test/herdr/` only with "see the exception in output 8", although outputs 7 and 10 also change it, which made acceptance criterion 13 read as if it covered `scenario.ts` and `smoke.ts`.

   **Applied:** section 4 annotates `test/core/` and `test/cli.test.ts` with outputs 7 and 8 and `test/herdr/` with outputs 7, 8 and 10. Output 8 and acceptance criterion 13 now cover only the tests that exist at the entry commit, other than `scenario.ts` and `smoke.ts`.

## Copilot review on PR #66, applied in revision 3

Date: 2026-11-24
Reviewer: GitHub Copilot, automated review on [PR #66](https://github.com/faelplg/demerzel/pull/66), against contract revision 2 at `192930b64df7e2344437a71985b1d0e42310f2e5`.
Outcome: the owner approved on 2026-11-24 at 07:32 BRT (UTC-3) accepting both High findings and fixing them in contract revision 3, before any Build and without reopening earlier owner decisions (section 18, decision 9, and refinement 8).

The comment bodies below are quoted as the orchestrator relayed them; no other Copilot text is reproduced.

1. **High - the label fallback is global** ([comment](https://github.com/faelplg/demerzel/pull/66#discussion_r4674741148), contract lines about 413 to 416).

   **Comment:** "The recovery fallback is global: a unique task-label tab in a different workspace is still eligible. S3 only rejects duplicate task labels; it does not require the one match to belong to this task's recorded `project_workspace`, so a partial `tab create` answer could make Demerzel record another project's tab and later close it. Scope this fallback to the recorded workspace ID, and carry the same constraint into V1 and X1."

   **Applied:** the new requirement F1 defines one label fallback, used only by the T4 failure path, recovery (V1) and `close` (X1), and only for a task that records `project_workspace` and has no `backend_ids.tab`. Its only candidates are tabs whose `workspace` equals `project_workspace.id`; a tab with the task label in any other workspace is never recorded, written to `backend_ids` or `created`, or closed. S3 now requires task-label uniqueness among the tabs of one workspace, so the same label in two workspaces is a valid snapshot and not `backend-unavailable`. T4, V1, V2, X1 and output 8 point to F1. A task recorded before 0.19 has no label fallback and keeps V3 and X6 (X6 now says so). Case (a) has a focused test, mutations and an acceptance criterion.

2. **High - the label fallback cannot tell the unit's tab from a human tab** ([comment](https://github.com/faelplg/demerzel/pull/66#discussion_r4674741194), contract lines about 462 to 465).

   **Comment:** "The label fallback is not safe enough to guarantee the contract's 'only the unit's tab' rule. S3 rejects duplicate task-shaped labels, but it does not distinguish a Demerzel tab from a human tab: if the real tab is missing from the snapshot and a human has one tab labeled `<task id> <agent name>`, that single tab passes S3 and X1/V1 will record or close it by label. Please define an ownership check for label-based recovery/close (or refuse when the candidate cannot be tied to the task's agent/pane) and add a test for this case; otherwise a human tab can be acted on as the unit's tab."

   **Applied:** S1 gives each snapshot agent the `tab` of its pane, which herdr's snapshot already carries. F2 is the ownership check: a candidate passes when it hosts no agent or only the task's recorded `agent_name`, and fails when it hosts any other agent, Demerzel's or not, alone or beside the task's own. F3 says what a failing candidate does: the T4 failure path records nothing; recovery does not adopt it and records `tab_not_owned: { tab, agents }` in its history detail; `close` refuses with the new core refusal `tab-not-owned`, exit `2`, with no effect, checked after `task-working` and before the recovery is published. F4 keeps a no-agent candidate acceptable, since it is the tab of a dispatch stopped before `agent start` and herdr 0.9.5 cannot tell it apart from an empty tab a human labeled the same way; no cwd, pane title, tab number or process heuristic is added. That residual risk is a known limitation in section 16. Cases (b) and (c) have focused tests, mutations and acceptance criteria; `tab-not-owned` joins outputs 1 and 3, the FAIL conditions and refinements 2 and 8.
